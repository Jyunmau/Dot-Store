# 后端服务架构重构计划

## 一、当前架构评估

### 1. 存在问题
- **模型定义重复**：`apps/api-server/models/` 和 `modules/` 目录中都定义了相同的模型
- **架构层次不清晰**：没有严格遵循三层架构设计，层间职责划分模糊
- **代码组织混乱**：业务逻辑、API路由、数据模型混合在一起
- **缺少明确的接口定义**：API直接操作数据库，没有通过业务逻辑层
- **跨层依赖**：存在直接跨层调用的情况

### 2. 架构设计目标
- 严格遵循三层架构设计：Kernel层、platform层、script层
- 实现层间通过明确定义的接口通信
- 消除跨层直接调用和循环依赖
- 实现高内聚低耦合的设计原则
- 提高代码的可维护性和可扩展性
- 确保重构后可通过Docker正常启动和运行
- 兼容1.1版本需求

## 二、重构方案

### 1. 目录结构调整

创建三个独立的根文件夹，分别对应三层架构：

```
Dot-Store/
├── kernel/              # Kernel层：商业计算内核（去行业）
│   ├── models/          # 数据模型定义
│   │   ├── resource.py  # 资源模型
│   │   ├── resource_event.py  # 资源占用事件模型
│   │   ├── account.py   # 账户模型
│   │   ├── ledger.py    # 账本模型
│   │   └── audit.py     # 审计模型
│   ├── services/        # 数据处理服务
│   └── utils/           # 工具函数
├── platform/            # Platform层：餐饮/酒吧行业OS
│   ├── models/          # 行业模型定义
│   │   ├── table.py     # 台位模型
│   │   ├── reservation.py  # 订台模型
│   │   ├── member.py    # 会员模型
│   │   ├── cashback.py  # 返现模型
│   │   └── order.py     # 订单模型
│   ├── services/        # 业务服务
│   ├── repositories/    # 数据访问层
│   ├── schemas/         # 数据传输对象
│   └── utils/           # 工具函数
├── script/              # script层：HTTP请求处理
│   ├── routes/          # API路由
│   ├── middlewares/     # 中间件
│   ├── schemas/         # 请求响应模型
│   └── utils/           # 工具函数
├── shared/              # 共享资源
│   ├── db/              # 数据库配置
│   ├── config/          # 配置管理
│   └── exceptions/      # 异常定义
├── apps/                # 保留原有apps目录，用于存放Docker配置和启动脚本
│   └── api-server/      # 仅保留Dockerfile和启动脚本
└── docker-compose.yml   # Docker-compose配置文件
```

### 2. 各层职责定义

#### (1) Kernel层
- **职责**：底层数据处理、原子能力提供、数据计算
- **核心组件**：
  - 资源系统（Resource）：资源的CRUD操作
  - 资源占用事件（ResourceEvent）：事件的写入与查询
  - 账户与数值系统（Account + Ledger）：账户管理和数值记账
  - 交易与可靠性：事件的可靠写入和幂等性保证
  - 审计日志：关键操作的审计记录
- **边界限制**：
  - 不包含任何行业特定语义
  - 不定义业务规则
  - 不提供UI界面

#### (2) Platform层
- **职责**：业务逻辑处理、事务管理、服务编排
- **核心组件**：
  - 行业资源建模：Resource → Table映射
  - 行业身份系统：游客 → 会员 → 股东
  - 行业规则：订台规则、消费规则、返现/抵扣规则
  - 会员/股东系统：会员等级和身份管理
  - 返现政策：基于消费的返现规则
  - 抵扣政策：积分/余额抵扣规则
  - 订台服务：订台流程和状态管理
- **边界限制**：
  - 仅支持餐饮/酒吧行业
  - 不包含门店特定的定制化规则
  - 不支持非行业共识的业务模型

#### (3) script层
- **职责**：HTTP请求处理、请求验证、响应格式化
- **核心组件**：
  - API路由定义
  - 请求响应模型
  - 中间件
- **边界限制**：
  - 不处理高并发或关键业务流程
  - 不提供长期稳定的业务支持
  - 不修改或污染Platform层的核心业务模型

### 3. 层间交互机制

- **script层** → **Platform层**：通过业务服务接口调用
- **Platform层** → **Kernel层**：通过数据服务接口调用
- **层间通信**：使用明确的接口定义，避免直接调用底层实现

### 4. 重构步骤

#### 步骤1：创建新的目录结构
- 创建kernel、platform、script三个根目录
- 创建各层内部的子目录结构
- 移动共享资源到shared目录

#### 步骤2：迁移和重构Kernel层
- 迁移数据模型定义到kernel/models/
- 实现资源系统、账户与数值系统、交易与可靠性、审计日志等核心功能
- 确保Kernel层不包含任何行业特定语义

#### 步骤3：迁移和重构Platform层
- 迁移业务逻辑到platform/services/
- 实现数据访问层platform/repositories/
- 定义业务服务接口
- 实现行业资源建模、行业身份系统、行业规则等功能
- 确保Platform层只包含行业共识的业务逻辑

#### 步骤4：迁移和重构script层
- 迁移API路由到script/routes/
- 实现请求响应模型script/schemas/
- 重构控制器，通过业务服务接口调用业务逻辑
- 确保script层只处理HTTP请求和响应

#### 步骤5：定义层间接口
- 为各层定义明确的接口
- 实现接口适配器
- 确保层间通信遵循依赖倒置原则

#### 步骤6：更新Docker配置
- 更新API服务的Dockerfile，适配新的目录结构
- 确保docker-compose.yml可以正确构建和启动重构后的服务
- 添加必要的环境变量配置

#### 步骤7：添加文档和注释
- 为各模块添加功能说明
- 为接口添加详细注释
- 编写架构说明文档

#### 步骤8：测试和验证
- **单元测试**：运行各模块的单元测试
- **Docker构建测试**：使用docker-compose构建镜像
- **Docker启动测试**：使用docker-compose启动所有服务
- **API接口测试**：通过HTTP请求测试API接口
- **业务逻辑验证**：验证核心业务逻辑的正确性

### 2. API接口定义

#### 订单API
- **创建订单**：`POST /api/orders`
  - 请求体：`{"shop_id": int, "amount_estimate": float, "tags": list, "metadata": dict}`
  - 响应：`{"id": int, "message": string}`

- **获取订单详情**：`GET /api/orders/{id}`
  - 响应：`{"id": int, "shop_id": int, "status": string, "amount_estimate": float, "amount_actual": float, "tags": list, "metadata": dict, "created_at": string, "updated_at": string}`

- **更新订单**：`PUT /api/orders/{id}`
  - 请求体：`{"status": string, "amount_actual": float, "tags": list, "metadata": dict}`
  - 响应：`{"id": int, "message": string}`

- **获取订单列表**：`GET /api/orders?shop_id={shop_id}`
  - 响应：`[{"id": int, "shop_id": int, "status": string, "amount_estimate": float, "tags": list, "metadata": dict, "created_at": string, "updated_at": string}]`

#### 订台API
- **创建订台**：`POST /api/reservations`
  - 请求体：`{"shop_id": int, "table_id": int, "member_id": int, "start_time": string, "end_time": string, "people_count": int}`
  - 响应：`{"id": int, "message": string}`

- **获取订台详情**：`GET /api/reservations/{id}`
  - 响应：`{"id": int, "shop_id": int, "table_id": int, "member_id": int, "status": string, "start_time": string, "end_time": string, "people_count": int, "created_at": string}`

- **更新订台状态**：`PUT /api/reservations/{id}/status`
  - 请求体：`{"status": string}`
  - 响应：`{"id": int, "message": string}`
