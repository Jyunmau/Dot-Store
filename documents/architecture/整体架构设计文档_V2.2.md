## 1. 架构概述

### 1.1 架构理念

Dot-Store V2.2 采用 **三层数据模型架构**（Three-Layer Data Model Architecture），在V2.1多模块单体架构基础上，实现财务强一致性、事件驱动可追溯、支持AI推理的架构升级。

**核心设计理念：**

1. **财务强一致性（可审计）**：所有余额类字段必须可由流水重建，禁止直接修改余额
2. **事件驱动可追溯**：所有关键行为写入经营事件日志，支持完整的事件追溯
3. **支持未来AI推理**：预留完整的AI推理接口，支持AI读取JSON payload
4. **可演进（不推翻重来）**：数据结构支持未来演进，不需要推翻重来
5. **模块边界清晰**：每个模块负责特定的业务领域
6. **运维简单**：单体架构部署简单，运维成本低

### 3.2 架构特点

1. **三层数据模型**：交易事实层 → 结构状态层 → 智能分析层
2. **多模块单体**：所有模块在一个代码库中，但有清晰的边界
3. **分层架构**：客户端层 → 前端应用层 → 后端应用层 → 数据层 → 基础设施层
4. **模块间通信**：通过接口通信，而非直接操作数据库
5. **数据流向**：前端通过API调用后端，后端操作数据库，返回数据给前端
6. **缓存策略**：使用Redis缓存热点数据，提高性能
7. **监控体系**：全栈监控，包括前端、后端、数据库、基础设施
8. **MCP服务**：支持AI Agent通过MCP协议调用系统功能

## 4. 三层数据模型架构

### 4.1 架构设计

V2.2版本采用**三层数据模型架构**，满足财务强一致性、事件驱动可追溯、支持AI推理的设计原则。

```
┌─────────────────────────────────────────────────────────────────┐
│ 1️⃣ 交易事实层（Transaction Fact Layer - 不可篡改）              │
│ ┌─────────────────────────────────────────────────────────────┐ │
│ │ - orders（订单）                                            │ │
│ │ - order_items（订单项）                                      │ │
│ │ - payments（支付记录）                                       │ │
│ │ - inventory_transactions（库存流水）                         │ │
│ │ - customer_account_transactions（账户流水）                  │ │
│ │ - cash_transactions（现金流水）                              │ │
│ │ - business_events（经营事件日志）                            │ │
│ └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
                              │
                              │ 驱动
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ 2️⃣ 结构状态层（Structure State Layer - 可重建）                 │
│ ┌─────────────────────────────────────────────────────────────┐ │
│ │ - inventory_items（库存状态）                                │ │
│ │ - customer_accounts（客户账户状态）                          │ │
│ │ - cash_accounts（现金账户状态）                              │ │
│ │ - expense_records（成本记录）                                │ │

│ └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘

                              │ 读取
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ 3️⃣ 智能分析层（Intelligence Analysis Layer - 衍生数据）         │
│ ┌─────────────────────────────────────────────────────────────┐ │
│ │ - decision_logs（决策日志）                                  │ │
│ │ - cash_flow_predictions（现金流预测）                        │ │
│ │ - risk_alerts（风险预警）                                    │ │
│ └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 核心设计原则

#### 4.2.1 财务强一致性（可审计）

**原则说明**：
- 所有余额类字段必须可由流水重建
- 禁止直接修改余额字段
- 所有余额变更必须通过流水记录触发

**实现方式**：
```python
# 禁止操作
# inventory_items.quantity = 100  # 直接修改余额 - 禁止

# 允许操作
# 创建库存流水，自动更新库存状态
inventory_transaction = InventoryTransaction(
    product_id=1,
    change_qty=10,  # 入库10个
    change_type="purchase",
    unit_price=50.00
)
db.add(inventory_transaction)
db.commit()
# 库存状态由流水聚合计算：quantity = SUM(change_qty)
```

#### 4.2.2 事件驱动可追溯

**原则说明**：
- 所有关键行为写入 business_events 事件日志
- 事件日志不可篡改、不可删除
- 支持完整的事件追溯和审计

**实现方式**：
```python
# 订单创建时写入事件日志
business_event = BusinessEvent(
    store_id=user_id,
    event_type="order_created",
    related_entity="order",
    related_id=order.id,
    event_payload={
        "order_id": order.id,
        "amount": float(order.amount),
        "order_type": order.order_type,
        "created_at": order.created_at.isoformat()
    }
)
db.add(business_event)
```

#### 4.2.3 支持未来AI推理

**原则说明**：
- 预留完整的AI推理接口
- 支持AI读取JSON payload
- 事件日志包含完整的上下文信息

**实现方式**：
```python
# MCP服务提供AI推理接口
@router.get("/ai/events")
async def get_events_for_ai(
    event_type: Optional[str] = None,
    start_date: Optional[date] = None,
    end_date: Optional[date] = None
):
    """AI推理接口 - 获取事件日志"""
    events = await event_service.get_events(
        event_type=event_type,
        start_date=start_date,
        end_date=end_date
    )
    return {"events": [e.event_payload for e in events]}
```

#### 4.2.4 可演进（不推翻重来）

**原则说明**：
- 数据结构支持未来演进
- 不需要推翻重来
- 保持向后兼容性

**实现方式**：
- 使用JSON字段存储扩展数据
- 预留扩展字段
- 版本化API设计

### 4.3 数据一致性保障机制

#### 4.3.1 余额字段一致性规则

| 数据表 | 余额字段 | 对应流水表 | 一致性要求 |
|--------|---------|-----------|-----------|
| inventory_items | quantity | inventory_transactions | quantity = SUM(change_qty) |
| customer_accounts | balance_amount | customer_account_transactions | balance = SUM(change_amount) |
| customer_accounts | liability_amount | customer_account_transactions | liability = SUM(待消耗金额) |
| cash_accounts | balance | cash_transactions | balance = SUM(change_amount) |

#### 4.3.2 禁止操作

- 禁止直接修改 inventory_items.quantity
- 禁止直接修改 customer_accounts.balance_amount
- 禁止直接修改 customer_accounts.liability_amount
- 禁止直接修改 cash_accounts.balance
- 禁止删除流水记录
- 禁止删除事件日志

#### 4.3.3 允许操作

- 允许创建流水记录
- 允许创建事件日志
- 允许通过创建调整记录来修正错误

## 5. 模块划分与边界

### 5.1 模块划分

| 模块名称 | 主要职责 | 核心功能 | 数据层级 | 依赖关系 |
|---------|---------|---------|---------|----------|

| **客户账户模块** | 客户预收权益管理 | 账户流水、账户状态、充值消费 | 交易事实层+结构状态层 | 依赖认证模块 |
| **现金账户模块** | 现金流管理 | 现金流水、账户状态 | 交易事实层+结构状态层 | 依赖认证模块 |
| **成本记录模块** | 成本管理 | 成本录入、成本分析 | 结构状态层 | 依赖认证模块 |
| **财务快照模块** | 财务快照生成 | 每日快照、快照对比 | 结构状态层 | 依赖所有业务模块 |
| **现金流分析模块** | 现金流分析 | 预测、风险预警、盈亏平衡 | 智能分析层 | 依赖所有业务模块 |
| **事件日志模块** | 事件日志管理 | 事件记录、事件追溯 | 交易事实层 | 依赖所有业务模块 |

| **备份模块** | 数据备份与恢复 | 手动备份、自动备份、数据恢复 | - | 依赖所有业务模块 |

### 5.2 模块边界规则

**强制规则：**
1. **认证模块**：负责用户认证和权限管理，其他模块通过接口获取用户信息
2. **订单模块**：订单创建时自动创建支付记录、写入事件日志
3. **库存模块**：库存变动必须通过流水记录，禁止直接修改库存状态
4. **客户账户模块**：账户变动必须通过流水记录，禁止直接修改账户状态
5. **现金账户模块**：现金变动必须通过流水记录，禁止直接修改账户状态
6. **财务快照模块**：只读模块，定时生成快照，不能修改业务数据
7. **现金流分析模块**：只读模块，读取业务数据进行分析，不能修改业务数据
8. **事件日志模块**：只写模块，记录所有关键行为，不能修改业务数据
9. **MCP服务模块**：作为独立入口，复用业务模块的服务层
10. **备份模块**：可以读取所有模块的数据，但不能修改业务逻辑

### 5.3 模块间通信机制

**服务接口设计：**
1. **接口定义**：每个模块暴露清晰的服务接口，使用抽象基类定义
2. **依赖注入**：使用依赖注入容器管理模块间依赖
3. **异常处理**：模块间通信的异常需要统一处理
4. **超时机制**：设置合理的通信超时时间（默认5秒）
5. **接口版本控制**：接口变更时保持向后兼容

**通信方式：**
1. **同步调用**：适用于实时性要求高的场景，如权限验证
2. **异步事件**：适用于非实时性场景，如订单创建后写入事件日志
3. **定时任务**：适用于周期性任务，如每日生成财务快照

### 5.4 事件驱动架构（P0优化）

为降低模块耦合度，V2.2版本采用事件驱动架构实现模块间解耦。

#### 5.4.1 事件总线设计

```python
# app/core/event_bus.py
from typing import Callable, Dict, List
from dataclasses import dataclass
from datetime import datetime
import asyncio

@dataclass
class DomainEvent:
    """领域事件基类"""
    event_type: str
    aggregate_type: str
    aggregate_id: int
    payload: dict
    timestamp: datetime = None
    
    def __post_init__(self):
        if self.timestamp is None:
            self.timestamp = datetime.utcnow()

class EventBus:
    """事件总线"""
    
    def __init__(self):
        self._handlers: Dict[str, List[Callable]] = {}
    
    def subscribe(self, event_type: str, handler: Callable):
        """订阅事件"""
        if event_type not in self._handlers:
            self._handlers[event_type] = []
        self._handlers[event_type].append(handler)
    
    async def publish(self, event: DomainEvent):
        """发布事件"""
        handlers = self._handlers.get(event.event_type, [])
        for handler in handlers:
            try:
                if asyncio.iscoroutinefunction(handler):
                    await handler(event)
                else:
                    handler(event)
            except Exception as e:
                logger.error(f"事件处理失败: {event.event_type}, {e}")

# 全局事件总线实例
event_bus = EventBus()
```

| `order_completed` | 订单完成 | 事件日志模块 | 记录经营事件 |

```python
from datetime import datetime

class OptimisticLockMixin:
    """乐观锁混入类"""
    version = Column(Integer, default=1, nullable=False)
    
    def check_version(self, expected_version: int):
        """检查版本号"""
        if self.version != expected_version:
            raise ConcurrentModificationError(
                f"数据已被其他操作修改，当前版本: {self.version}, 期望版本: {expected_version}"
            )
    
    def increment_version(self):
        """递增版本号"""
        self.version += 1

# 使用示例

    account.check_version(expected_version)
    
    # 更新数据
    for key, value in data.items():
```

#### 5.5.3 分布式锁实现

```python
# app/core/distributed_lock.py
import redis
from contextlib import asynccontextmanager
from app.core.config import settings

class DistributedLock:
    """分布式锁"""
    
    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
    
    @asynccontextmanager
    async def acquire(self, key: str, timeout: int = 10, retry_times: int = 3):
        """获取分布式锁"""
        lock_key = f"lock:{key}"
        lock_value = str(uuid.uuid4())
        
        for _ in range(retry_times):
            acquired = self.redis.set(
                lock_key, lock_value, nx=True, ex=timeout
            )
            if acquired:
                try:
                    yield
                    return
                finally:
                    # 释放锁（使用Lua脚本保证原子性）
                    self.redis.eval(
                        "if redis.call('get', KEYS[1]) == ARGV[1] then "
                        "return redis.call('del', KEYS[1]) else return 0 end",
                        1, lock_key, lock_value
                    )
            await asyncio.sleep(0.1)
        
        raise LockAcquireError(f"获取锁失败: {key}")

# 使用示例
async def create_order_with_lock(user_id: int, data: OrderCreate):
    """创建订单 - 使用分布式锁"""
    lock = DistributedLock(redis_client)
    
    async with lock.acquire(f"order:create:{user_id}"):
        # 在锁保护下执行订单创建
        order = await order_service.create_order(user_id, data)
        return order
```

### 9.3 MCP认证方案

采用API Key模式：

```python
# MCP认证流程
# 1. 客户端在请求头中携带 X-API-Key
# 2. 后端验证API Key并转换为user_id
# 3. 后续业务操作使用转换后的user_id

async def authenticate_by_api_key(db: Session, api_key: str) -> Optional[int]:
    """通过API Key认证用户"""
    if not api_key:
        return None
    
    api_key_hash = hashlib.sha256(api_key.encode()).hexdigest()
    user = db.query(User).filter(User.api_key_hash == api_key_hash).first()
    
    if not user:
        return None
    
    return user.id
```

```python
    'api_request_total',
    'API请求总数',
    ['method', 'endpoint', 'status']

    'api_request_duration_seconds',
    'API请求耗时',
    ['method', 'endpoint'],
    buckets=[0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0]

db_query_duration = Histogram(
    'db_query_duration_seconds',

    'cash_balance_total',
    '现金余额',
    ['user_id']
)

safety_index_gauge = Gauge(
    'safety_index',
    '安全指数',
    ['user_id']
)

# 监控装饰器
def monitor_api(endpoint: str):
    """API监控装饰器"""
    def decorator(func):
        @wraps(func)
        async def wrapper(*args, **kwargs):
            start_time = time.time()
            status = 200
            try:
                result = await func(*args, **kwargs)
                return result
            except Exception as e:
                status = 500
                raise
            finally:
                duration = time.time() - start_time
                api_request_count.labels(
                    method=func.__name__,
                    endpoint=endpoint,
                    status=status
                ).inc()
                api_request_duration.labels(
                    method=func.__name__,
                    endpoint=endpoint
                ).observe(duration)
        return wrapper
    return decorator
```

## 11. 安全设计

1. **密码安全**：
   - 使用bcrypt加密存储密码
   - 密码复杂度要求（至少8位，包含字母和数字）
   - 密码重置需要验证身份

   - 使用HTTPS加密传输
   - 避免在URL中传递敏感信息
   - 合理设置Cookie属性（HttpOnly, Secure, SameSite）

3. **数据存储**：
   - 敏感数据加密存储
   - 不同用户数据完全隔离
   - 定期备份数据

### 11.2 认证与授权

1. **认证**：
   - JWT Token认证
   - Token过期时间设置（7天）
   - 刷新Token机制
   - 登录失败5次后锁定账户30分钟

2. **授权**：
   - 基于角色的访问控制（RBAC）
   - 细粒度权限控制
   - API权限验证

1. **余额保护**：

   - 异步处理
   - 请求限流

### 12.3 财务快照优化

1. **定时生成**：
   - 每日凌晨2点生成财务快照
   - 避免高峰期计算

2. **缓存策略**：
   - 仪表盘优先读取快照数据
   - 快照数据缓存5分钟

3. **增量计算**：
   - 只计算当天变更的数据
   - 基于前一天快照增量更新
