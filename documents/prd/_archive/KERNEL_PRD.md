Dot-Store Kernel 层产品需求文档（PRD）

本文档描述 Dot-Store Kernel 层的产品需求与功能设计。

面向对象：产品设计 / 工程实现 / 未来合作者

⸻

1. 产品愿景与边界

1.1 产品愿景

Kernel 层是 Dot-Store 的商业计算内核，提供抽象的、去行业化的原子能力，为上层 Platform 和 App-Script 层提供稳定、可靠的基础支撑。

1.2 核心价值主张
1. 提供稳定的原子能力
2. 保证系统可靠性和数据完整性
3. 保持去行业化，不被特定业务场景污染
4. 支持高并发和异构行业扩展

1.3 明确不做的事情
- ❌ 不实现行业特定语义（如"酒台"、"会员等级"）
- ❌ 不定义业务规则（如"返现比例"、"最低消费"）
- ❌ 不提供行业特定的 UI 界面
- ❌ 不参与业务流程决策

2. 目标用户

Kernel 层的直接用户是 Platform 和 App-Script 层的开发者，而非最终业务用户。

3. 核心模块与功能

3.1 资源系统（Resource）

3.1.1 模块定位
提供抽象的资源管理能力，不包含任何行业语义。

3.1.2 核心功能
- 资源的创建、读取、更新、删除（CRUD）
- 资源状态的派生计算
- 资源的所有权管理

3.1.3 数据模型
```
Resource
- id: string (唯一标识符)
- type: string (资源类型，无语义约束)
- owner_id: string (资源所有者 ID)
- status: string (派生状态：available, occupied, expired)
```

3.1.4 设计原则
- 资源是抽象的、不可消耗的实体
- 不包含容量、价格、空间关系等行业属性
- 资源状态由 ResourceEvent 派生

3.2 资源占用事件（ResourceEvent）

3.2.1 模块定位
记录资源的占用、释放、过期、取消等事件，采用 Event-first 设计理念。

3.2.2 核心功能
- 资源占用事件的写入与查询
- 并发冲突检测（同一资源、重叠时间）
- 事件驱动的状态更新

3.2.3 数据模型
```
ResourceEvent
- id: string (唯一标识符)
- resource_id: string (关联资源 ID)
- account_id: string (操作账户 ID)
- event_type: string (事件类型：occupy, release, expire, cancel)
- intent_id: string (操作意图 ID)
- timestamp: datetime (事件时间戳)
- metadata: json (扩展元数据)
```

3.2.4 设计原则
- 占用是事件，不是状态
- 状态由事件流计算派生
- 支持高并发场景下的事件写入

3.3 账户与数值系统（Account + Ledger）

3.3.1 模块定位
提供账户管理和数值记账能力，不包含具体业务语义。

3.3.2 核心功能
- 账户的创建、读取、更新、删除（CRUD）
- 数值的增加、减少、查询
- 数值类型的命名空间管理
- 汇率配置接口

3.3.3 数据模型
```
Account
- id: string (唯一标识符)
- owner_id: string (账户所有者 ID)
- role: string (角色：user, admin, system)

LedgerEntry
- id: string (唯一标识符)
- account_id: string (关联账户 ID)
- value_type: string (数值类型，命名空间)
- delta: number (数值变化量)
- source: string (变化来源)
- timestamp: datetime (记录时间戳)
```

3.3.4 设计原则
- 不包含"积分"、"余额"、"返点"等业务语义
- value_type 只是命名空间，由上层赋予业务含义
- 支持多种数值类型的独立记账

3.4 交易与可靠性（Transaction & Reliability）

3.4.1 模块定位
保证系统的交易可靠性和数据完整性。

3.4.2 核心功能
- 事件的可靠写入（不丢记录）
- 操作的幂等性保证
- 数据的可追溯和可回放
- 事务支持

3.4.3 设计原则
- 不负责解释业务含义
- 只保证数据的完整性和可靠性
- 支持数据的全量和增量同步

3.5 权限与授权（Auth & Permission）

3.5.1 模块定位
提供基础的权限管理和操作审计能力。

3.5.2 核心功能
- 多管理员支持
- 操作审计日志
- 权限角色管理（预留）

3.5.3 设计原则
- UI 可以不做，但模型必须存在
- 支持未来的权限扩展
- 记录所有关键操作的审计日志

4. 非功能需求

4.1 性能要求
- 支持每秒至少 1000 条事件写入
- 资源状态查询响应时间不超过 100ms
- 支持水平扩展

4.2 可靠性要求
- 数据持久化，保证不丢记录
- 支持事务回滚
- 系统可用性不低于 99.9%

4.3 安全性要求
- 数据传输加密
- 敏感数据存储加密
- 操作权限严格控制

4.4 可扩展性要求
- 支持新的资源类型扩展
- 支持新的数值类型扩展
- 支持事件类型的扩展

5. API 设计原则

5.1 接口风格
采用 RESTful API 风格，使用 JSON 格式进行数据交互。

5.2 版本管理
使用 API 版本号进行接口管理，确保向后兼容。

5.3 错误处理
统一的错误码和错误信息格式，便于上层系统处理。

5.4 认证授权
采用 JWT 或 OAuth 2.0 进行身份认证和授权。

6. 技术实现建议

6.1 数据存储
- 事件数据：使用时间序列数据库或消息队列
- 关系数据：使用关系型数据库（如 PostgreSQL）
- 缓存：使用 Redis 提高查询性能

6.2 架构风格
- 事件驱动架构
- 微服务架构（可选，根据规模）
- 支持水平扩展

6.3 开发语言
- 后端：Node.js 或 Go
- 数据库：PostgreSQL
- 缓存：Redis

7. 验收标准

7.1 功能验收
- 资源 CRUD 功能正常工作
- 资源占用事件能够正确记录和查询
- 并发冲突检测有效
- 账户与数值记账准确
- 数据可追溯和可回放

7.2 性能验收
- 事件写入性能达到要求
- 查询响应时间符合要求
- 系统能够稳定运行 7*24 小时

7.3 可靠性验收
- 系统故障后数据不丢失
- 事务回滚功能正常
- 系统恢复时间在可接受范围内

⸻

本 PRD 描述的是 Dot-Store Kernel 层的最小但完整产品形态。所有功能设计与工程实现应以此为依据，严格遵守去行业化的设计原则。
