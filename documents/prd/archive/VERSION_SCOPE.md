Dot-Store 版本范围说明文档

本文档描述 Dot-Store 当前版本的实现范围、边界和后续版本规划。

面向对象：产品设计 / 工程实现 / 项目管理 / 投资者

⸻

1. 版本概述

1.1 版本号
Dot-Store V2.0（分层架构版）

1.2 发布日期
预计发布日期：2024年12月

1.3 版本定位
本次版本升级是 Dot-Store 从单一行业解决方案向通用商业计算平台的重大转变，通过引入三层架构（Kernel、Platform、App-Script），实现系统的高度可扩展性和灵活性。

1.4 核心目标
1. 实现去行业化的 Kernel 层，提供稳定的原子能力
2. 构建餐饮/酒吧行业的 Platform 层，实现行业标准化
3. 提供灵活的 App-Script 层，支持门店定制和试验性创新
4. 保持与旧系统的兼容性，确保平滑迁移

2. 各层实现范围

2.1 Kernel 层

2.1.1 已实现功能
- ✅ 资源系统（Resource）：资源的 CRUD 操作
- ✅ 资源占用事件（ResourceEvent）：事件的写入与查询
- ✅ 并发冲突检测：同一资源、重叠时间的冲突处理
- ✅ 账户与数值系统（Account + Ledger）：账户管理和数值记账
- ✅ 交易与可靠性：事件的可靠写入和幂等性保证
- ✅ 审计日志：关键操作的审计记录

2.1.2 未实现功能（计划在 V2.1 实现）
- ⏳ 权限与授权：多角色权限管理（预留模型，尚未实现 UI）
- ⏳ 汇率配置接口：不同数值类型之间的汇率转换
- ⏳ 数据回放功能：基于事件流的数据回放能力

2.1.3 边界限制
- 不包含任何行业特定语义
- 不定义业务规则
- 不提供 UI 界面

2.2 Platform 层（餐饮/酒吧行业）

2.2.1 已实现功能
- ✅ 台位管理系统（Table / Booth）：台位的 CRUD 和区域管理
- ✅ 订台服务（Reservation Service）：订台流程和状态管理
- ✅ 会员/股东系统（Member / Shareholder）：会员等级和身份管理
- ✅ 返现政策（CashbackPolicy）：基于消费的返现规则
- ✅ 抵扣政策（RedemptionPolicy）：积分/余额抵扣规则
- ✅ 订单管理系统（Order）：订单的创建和状态管理

2.2.2 未实现功能（计划在 V2.1 实现）
- ⏳ 台位可视化配置界面：拖拽式台位布局配置
- ⏳ 会员等级晋升规则：基于消费的自动等级晋升
- ⏳ 多种支付方式集成：微信支付、支付宝支付等
- ⏳ 虚拟打印机订单推送：订单自动打印功能

2.2.3 边界限制
- 仅支持餐饮/酒吧行业
- 不包含门店特定的定制化规则
- 不支持非行业共识的业务模型

2.3 App-Script 层

2.3.1 已实现功能
- ✅ 规则脚本框架（Rule Script Framework）：脚本的执行和管理
- ✅ 脚本执行环境隔离：确保脚本不会影响核心系统
- ✅ 事件驱动机制：事件的发布和订阅
- ✅ 基础脚本模板库：提供常用脚本模板

2.3.2 未实现功能（计划在 V2.1 实现）
- ⏳ 门店 App 集成接口：完整的 App 注册和认证机制
- ⏳ 快速试验环境：试验性功能的快速部署和回滚
- ⏳ 在线脚本编辑器：可视化的脚本开发工具
- ⏳ 多语言 SDK 支持：提供 Python、Lua 等语言的 SDK

2.3.3 边界限制
- 不处理高并发或关键业务流程
- 不提供长期稳定的业务支持
- 不修改或污染 Platform 层的核心业务模型

3. 与旧系统的兼容性

3.1 数据兼容性
- 旧系统的用户数据将通过迁移脚本导入到新的 Account 系统
- 旧系统的订单数据将映射到新的 Order 系统
- 旧系统的会员数据将迁移到新的 Member 系统
- 迁移过程将确保数据的完整性和一致性

3.2 功能兼容性
- 旧系统的核心功能（订台、会员管理、返现等）将在新的 Platform 层实现
- 旧系统的 UI 界面将保持相似的用户体验，减少学习成本
- 旧系统的 API 将提供兼容层，确保第三方集成的平滑过渡

3.3 迁移计划
- 阶段 1：数据迁移（预计 1 周）
- 阶段 2：功能验证（预计 2 周）
- 阶段 3：灰度发布（预计 2 周）
- 阶段 4：全面切换（预计 1 周）

5. 风险与挑战

5.1 技术风险
- 三层架构的复杂性可能导致开发和维护成本增加
- 数据迁移过程中可能出现数据不一致或丢失
- 高并发场景下的性能挑战

5.2 业务风险
- 门店可能需要时间适应新的定制化开发方式
- 三层架构的概念可能需要更多的培训和教育
- 市场对通用商业计算平台的接受度有待验证

5.3 应对策略
- 提供详细的文档和培训材料
- 建立完善的测试和验证流程
- 采用渐进式发布策略，降低风险
- 建立快速响应的技术支持团队
