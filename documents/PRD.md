Dot-Store V1 产品需求文档（PRD）

本文档从业务需求与功能设计角度描述 Dot-Store V1。

面向对象：产品设计 / 工程实现 / 未来合作者

本 PRD 与《Architecture README》《Dev Guide · Final》共同构成 Dot-Store V1 的完整产品与工程定义。

⸻

1. 产品愿景与边界

1.1 产品愿景

Dot-Store 是一个面向 小微实体店铺 的轻量化经营记录与理解工具。

它的核心目标不是：
	•	管住老板
	•	规范流程
	•	复制大型企业 ERP

而是：

帮助老板从第一天开始，看清楚自己的生意，并且越用越清楚。

⸻

1.2 核心价值主张
	1.	开箱即用的账务可见性
	2.	接受真实世界的混乱，而不是强行规范
	3.	所有数据都可解释、可修正
	4.	记录成本低于人工记账

⸻

1.3 明确不做的事情（V1 边界）
	•	不追求流程标准化
	•	不做复杂库存 / 生产管理
	•	不做企业级权限体系
	•	不做强一致财务系统
	•	不假设稳定 SOP

⸻

2. 目标用户与使用场景

2.1 目标用户
	•	个体工商户
	•	小微餐饮 / 咖啡 / 奶茶 / 早餐店老板
	•	正在尝试创业、频繁试错的人

用户特征：
	•	强烈的现实盈利压力
	•	对数据有需求，但精力有限
	•	不具备专业财务或 IT 能力

⸻

2.2 核心使用场景
	•	每天结束时，想知道 今天赚了还是亏了
	•	想尝试新产品 / 新营销方式，但不确定是否值得
	•	账目混乱后，希望可以回溯与修正
	•	多种收入来源（堂食 / 外卖 / 活动）并存

⸻

3. 产品总览与模块划分

3.0 用户操作视角总览（先看这个）

从用户（店主）视角，Dot-Store V1 的核心操作非常有限，且不要求固定顺序：
	1.	记录一件事（哪怕不完整）
	•	新来了一单
	•	收到一笔钱
	•	花出去一笔钱
	2.	补充或修正记录
	•	晚点再填金额
	•	改标签、加备注
	•	发现记错了，手工调整
	3.	查看结果
	•	今天赚了还是亏了？
	•	钱主要花在哪？
	•	哪些尝试可能不划算？

Dot-Store 不要求用户理解“事件 / 订单 / 账务”的技术概念，
但用户的所有操作都会被系统自动映射到这些模块中。

⸻

3. 产品总览与模块划分

3.1 产品模块总览

Dot-Store V1 由以下核心模块组成：
	1.	Event（事件底座）
	2.	Order（订单与交易）
	3.	Ledger（分类账与账务）
	4.	Report（报表与视图）
	5.	Audit（审计与修正）
	6.	Config（基础配置）

模块关系：

Event  →  Order  →  Ledger  →  Report
              ↓
            Audit


⸻

4. 模块一：Event（事件底座）

4.0 用户如何触发 Event

用户不会直接操作 Event。

Event 由以下用户行为自动产生：
	•	创建订单
	•	新增账务分录
	•	导入外部数据

Event 的存在对用户是“不可见的”，但对系统是不可删除的事实记录。

⸻

4. 模块一：Event（事件底座）

4.1 模块定位

Event 是 Dot-Store 的 最底层事实记录层。

它代表：
	•	真实世界发生过的事情
	•	不带业务判断
	•	可能不完整、不规范

Event 不直接面向用户。

⸻

4.2 事件来源
	•	创建订单时自动生成
	•	手工补录（如线下活动）
	•	外部系统导入（如外卖平台数据）

⸻

4.3 事件特性
	•	允许延迟记录
	•	允许信息缺失
	•	只追加、不修改

⸻

5. 模块二：Order（订单与交易）

5.0 用户操作说明

从用户视角，Order 对应的是：

一次生意 / 一次交易 / 一次业务尝试

用户可以：
	•	快速创建一个订单（哪怕什么都不填）
	•	事后再补金额、标签、备注
	•	把多笔相关操作理解为“同一单生意”

系统不要求订单立即准确。

⸻

5. 模块二：Order（订单与交易）

5.1 模块定位

Order 是 业务理解层，是 Dot-Store 的业务锚点。

订单不要求完整：
	•	可以先存在，再补充
	•	可以只有标签，没有金额

⸻

5.2 订单生命周期（弱约束）
	•	Created（创建）
	•	Recorded（已记录）
	•	Adjusted（已调整）

状态仅用于辅助理解，不驱动强流程。

⸻

5.3 核心功能
	•	创建订单（快速记录）
	•	补充订单信息（金额 / 标签 / 备注）
	•	关联事件
	•	支持多来源订单（堂食 / 外卖 / 活动）

⸻

5.4 设计原则
	•	不强制实时结算
	•	不校验业务合理性
	•	不阻止“非常规操作”

⸻

6. 模块三：Ledger（分类账与账务）

6.0 用户操作说明

从用户视角，Ledger 对应的是：

钱的进出记录

用户可以直接：
	•	记一笔收入
	•	记一笔支出
	•	做一次盘盈 / 盘亏调整

这些操作：
	•	可以关联订单
	•	也可以完全独立存在

系统不会强制要求“每一笔钱都来自订单”。

⸻

6. 模块三：Ledger（分类账与账务）

6.1 模块定位

Ledger 是 Dot-Store 的 权威事实层。

它的目标不是实时准确，而是：

在复杂业务环境下，依然可以被理解和追溯。

⸻

6.2 分类账设计
	•	收入账
	•	成本账
	•	预充值 / 会员账
	•	临时账（活动 / 赠送）

不同账目相互隔离，避免总账污染。

⸻

6.3 分录原则
	•	每一笔钱 = 一条分录
	•	只追加、不修改
	•	可以关联订单，也可以独立存在

⸻

6.4 允许的现实情况
	•	手工盘盈 / 盘亏
	•	非订单收入
	•	临时赠送、非标准定价

⸻

7. 模块四：Report（报表与视图）

7.0 用户操作说明

从用户视角，Report 对应的是：

我现在生意的状态

用户可以：
	•	打开首页查看今日盈亏
	•	切换日期查看历史情况
	•	展开明细理解原因

用户不能直接修改 Report 中的数据，
所有修改必须回到 Order 或 Ledger 中完成。

⸻

7. 模块四：Report（报表与视图）

7.1 模块定位

Report 是 只读视图层，用于帮助老板理解当前状态。

⸻

7.2 核心报表
	•	今日盈亏
	•	收入结构（按账目 / 标签）
	•	成本结构

⸻

7.3 设计原则
	•	默认给结论
	•	明细可展开
	•	不做预测、不做建议（V1）

⸻

8. 模块五：Audit（审计与修正）

8.0 用户操作说明

从用户视角，Audit 对应的是：

我改过什么？为什么改？

用户可以：
	•	查看某条数据的修改历史
	•	理解当前数字是如何形成的

Audit 本身不产生业务数据，
只负责记录用户的修正行为。

⸻

8. 模块五：Audit（审计与修正）

8.1 模块定位

Audit 用于记录：
	•	数据修改
	•	人工修正行为

⸻

8.2 核心能力
	•	修改前 / 修改后记录
	•	修正路径可回溯
	•	不阻止修改，只记录修改

⸻

9. 模块六：Config（基础配置）

9.0 用户操作说明

Config 对应的是：

这个系统如何贴合我的生意

用户可以：
	•	定义常用账目分类
	•	配置常用标签
	•	调整基础业务类型

这些配置：
	•	不频繁
	•	不影响历史数据

⸻

9. 模块六：Config（基础配置）

9.1 模块定位

Config 用于承载 低频但必要的可配置项。

⸻

9.2 可配置内容（V1）
	•	分类账定义
	•	常用标签
	•	基础业务类型

⸻

10. 关键产品原则（总结）
	1.	记录优先于规范
	2.	可解释优先于准确
	3.	修正优先于约束
	4.	真实世界优先于系统优雅

⸻

本 PRD 描述的是 Dot-Store V1 的最小但完整产品形态。
所有功能设计与工程实现应以此为依据，而不是臆想中的未来规模。
