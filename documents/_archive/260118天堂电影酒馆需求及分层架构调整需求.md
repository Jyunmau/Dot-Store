# 天堂股东体验卡

为酒吧/夜店核心股东与会员打造的一站式会员管理与订台系统。支持 Web 端与微信小程序双端访问，提供可视化订台、会员周期管理、订单追踪与返现结算等核心功能。

## 功能特性

### 会员端
- 用户注册与登录（支持手机号认证）
- 可视化酒台预订（A/B/M 区域实时状态）
- 会员周期管理（月卡、季卡等套餐）
- 订单历史与消费记录查询
- 返现积分与钱包管理
- 响应式移动端优化体验

### 管理员端
- 可视化座位图管理（拖拽调整、实时同步）
- 预订审批与状态管理
- 订单流水查看与返现统计
- 会员账户管理
- 返现比例配置
- 虚拟打印机订单推送

### 支付集成
- 微信支付（Native/H5/JSAPI）
- 支付宝支付
- 支付回调与订单状态同步

1️⃣ Kernel 是否会被行业污染？

2️⃣ 资源占用是否有清晰的一阶模型？

	•	Kernel 提供 “数值账户 + 变换能力”
	•	分润 / 结算 延迟决策

这保证了演化权在你手里。

4️⃣ 管理后台是否被短期现实绑死？

➡️ 没有

你选择：
	•	现在：够用
	•	模型：预留
	•	UI：不背债

Ⅱ. Kernel 层规范（最重要部分）

1️⃣ Kernel 的合法职责清单

Kernel 只能提供以下能力：

（1）资源（Resource）
	•	抽象的、不可消耗的实体
	•	不包含：
	•	行业名称
	•	容量
	•	价格
	•	空间关系

Resource
- id
- type (string, 无语义约束)
- owner_id
- status (derived)


⸻

（2）资源占用事件（ResourceEvent）

占用是事件，不是状态

ResourceEvent
- id
- resource_id
- account_id
- event_type (occupy / release / expire / cancel)
- intent_id
- timestamp
- metadata (json)

	•	高并发时：
	•	先写事件
	•	状态由事件流计算
	•	是否实时，由实现决定，不由模型决定

⸻

（3）账户与数值（Account + Ledger）

Kernel 中 不存在“积分”“余额”“返点”这些词。

只存在：

Account
- id
- owner_id
- role (user / admin / system)

LedgerEntry
- id
- account_id
- value_type (string)
- delta
- source
- timestamp

	•	value_type 只是 命名空间
	•	“汇率”是 数值变换规则
	•	语义由 Platform / App 赋予

⸻

（4）交易与审计

Kernel 负责：
	•	不丢记录
	•	可追溯
	•	可回放

但 不负责解释业务含义。

⸻

（5）权限与授权（预留）
	•	支持多管理员
	•	支持操作审计
	•	UI 可以不做
	•	模型必须存在

⸻

Ⅲ. Platform 层规范（餐饮 / 酒吧）

Platform 是 第一个“发行版 OS”。

1️⃣ 资源具体化

Kernel	Platform
Resource	Table / Booth
Account	Member / Shareholder

	•	台位规则
	•	订台逻辑
	•	行业共识能力

⸻

2️⃣ 会员 / 股东模型
	•	游客 → 会员 → 股东
	•	是 Platform 的身份语义
	•	Kernel 只知道 Account

⸻

3️⃣ 返点 / 抵扣
	•	使用 Kernel 的 Ledger
	•	Platform 负责：
	•	命名
	•	汇率
	•	统计
	•	结算策略（当前即时）

⸻

Ⅳ. App / Script 层规范（未来重点）

定位

“门店的可编程行为层”

	•	快速实现新业态
	•	快速验证
	•	不污染 Platform

示例能力
	•	特定订台数量触发奖励
	•	时间衰减规则
	•	私有会员策略

演进路径
	•	Code → Script
	•	Script → 平台能力
	•	平台能力 → 内核能力（极少）

⸻

Ⅴ. 数据迁移与异构系统兼容原则

迁移总原则

允许结构重建，不允许语义丢失

具体规则
	1.	旧表 → 新表允许拆分
	2.	不保留旧字段名，但保留语义映射
	3.	关键行为必须能回放（Event 重建）
	4.	迁移脚本是一次性的，但可重跑

⸻

Ⅵ. UI / UX 的最终取舍结论
	•	会员端优先
	•	管理端够用
	•	所有复杂性优先隐藏在模型，而不是 UI
